## Security baseline — verified live

Ran `next start` (production build) and exercised the API with curl using real admin and employee logins.

### Fixed since the last review (IMPROVEMENT_NEEDED.md P0s) — confirmed by testing

1. **Tokens are now HMAC-SHA256 signed** (`lib/token.ts`), verified in both Edge middleware and route handlers.
   - Forged unsigned base64 token (the old P0 exploit) → **401** ✔
   - Signature-tampered token → **401** ✔
   - Unauthenticated `/api/*` → **401** ✔
2. **Production refuses to boot auth without `TOKEN_SECRET`.** With no env var and `NODE_ENV=production`, login throws `TOKEN_SECRET must be set in production` (500). No demo-secret fallback in prod ✔
3. **Route-level RBAC exists and holds** for the sensitive routes previously flagged. With an *employee* token:
   - PUT/DELETE `/api/employees/[id]` → 403; GET other employee → 403; GET own record → 200 ✔
   - PUT `/api/company`, `/api/settings/*`, GET `/api/administration`, POST `/api/administration/reset`, GET `/api/reports`, `/api/employees/export`, POST `/api/employees/import` → 403 ✔
   - Leave approve for another employee → 403; create leave for another employee → 403; cancel another's leave → 403 ✔
   - Payslip of another employee → 403; clock-in for another employee → 403 ✔
   - `/api/payroll/salaries` correctly self-scoped (1 row for employee, 8 for admin) ✔
4. **Passwords hashed with scrypt** (`lib/passwords.ts`), constant-time compare, legacy plaintext auto-rehash on login. Seed data still plaintext until first login (acceptable for demo seeds).
5. **Gmail OAuth callback now verifies `state`** (`verifyOAuthState`), refresh tokens encrypted at rest (AES-256-GCM keyed from TOKEN_SECRET, `lib/crypto-utils.ts`).
6. **State-changing GET removed**: `GET /api/documents?type=reminders` → 405 "Use POST /api/documents/reminders" ✔
7. `.gitignore` now excludes `data/`, `cookies.txt`, `db.json`, `secret.key`; no tracked secrets found in git ✔
8. Import upload has MIME + 10 MB size + row checks ✔

### New findings (this review)

**P1 — cross-employee data disclosure (verified live with an employee token):**

| Endpoint | Leak |
|---|---|
| `GET /api/dashboard` | Returns company-wide `totalPayroll`, `avgSalary`, per-department payroll, and *other employees' pending leaves* to any authenticated user, including plain employees. `getDashboardData()` takes no auth scope. |
| `GET /api/leaves` | Returns **all employees' leave requests** (types incl. sick leave, statuses, dates) to any authenticated user. GET is auth-only; POST/PUT are properly scoped, but the list itself is not. |
| `GET /api/email/gmail` | Returns Gmail connection status (`configured`/`connected`, 200) to a plain employee. `authUrl` is correctly withheld, but connection state should be `settings:manage`-only. |
| `GET /api/todos`, `/api/communication`, `/api/documents`, `/api/lifecycle` | Company-wide lists visible to plain employees. Company documents may be intentional; lifecycle records of other employees likely are not. |

Suggested smallest safe fix (not applied, per playbook rule to not expand a review task): scope `GET /api/leaves` and the dashboard payload by `auth.role`/`auth.employeeId` the same way `GET /api/employees` and `/api/payroll/salaries` already do.

**P2 — dependency advisories (`npm audit --omit=dev`, 4 high):**
- `next@14.2.35` — multiple advisories (DoS, cache poisoning, request smuggling in rewrites). Most require self-hosting features this app doesn't use, but a patch-level bump within 14.2.x/14.x should be scheduled with a dedicated compatibility pass (playbook: keep broad upgrades out of quick fixes).
- `nanoid <3.3.18` (transitive via postcss) — `npm audit fix` compatible.
- `xlsx@0.18.5` — prototype pollution + ReDoS, **no fixed npm release**; imports are HR-admin-gated and size-capped which mitigates, but consider `exceljs` or the vendor's own CDN build long-term.

**P3 — notes:**
- `next start` warns: `"next start" does not work with "output: standalone"` — Docker uses standalone correctly; harmless in dev but worth knowing.
- No security headers/CSP, no rate limiting on `/api/auth/login` (playbook baseline calls for rate limiting before internet-facing deployment).
- Login returns raw 500 (unhandled throw) when `TOKEN_SECRET` is missing in prod — correct behavior, but a fail-fast check at boot would surface the misconfiguration sooner and cleaner.
- Company scoping is still hard-coded `demo-company` in several engines — known deferred item (multi-tenant is out of scope per playbook).
